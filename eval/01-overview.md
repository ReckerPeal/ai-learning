# 01 · 概览与心智模型

## 1. 为什么 LLM Eval 这么难

传统 ML 评测有标准答案：分类问题看 accuracy / F1，回归看 RMSE，端到端跑就行。

LLM 应用不一样：

| 维度 | 传统 ML | LLM 应用 |
|---|---|---|
| 输出空间 | 离散 / 连续小空间 | **自然语言**（无穷大） |
| 标准答案 | 唯一 | 同一问题**多种合理答案** |
| 评判 | 自动可比 | 大多数情况**只能由人或 LLM 判断** |
| 一次评测的成本 | 低（推理） | 高（要调 LLM 当 judge） |
| 输入分布 | 训练时已知 | 用户会**问任何东西**，分布漂移严重 |
| 可重现性 | 高（确定性算子） | 弱（temperature、模型版本、上下文都影响） |
| 故障模式 | 数学上的误差 | 幻觉、偏题、风格崩坏、有害内容、prompt 注入...... |

**结论**：LLM eval 不是把 ML eval 直接套过来，需要专门的方法论。

## 2. 评测的三个层次

把 LLM 应用想成"组件 → 系统 → 用户"三层，每层评测目标不同：

### 2.1 组件级（Component-level）

单个 prompt、单个工具、单个 RAG 检索器——**一次只看一个 Runnable**。

- 输入输出可控
- 评测集小、跑得快、可单测
- 适合 CI / 开发循环

例子：
- 给定 query，retriever 召回的文档相关度
- 给定上下文，QA 链的答案 faithfulness
- 给定问题，classifier 的标签是否准确

### 2.2 系统级（System-level）

端到端的 RAG / Agent / Workflow——**多个组件串起来跑**。

- 输入输出更接近真实
- 评测集要更接近用户分布
- 跑起来慢、贵
- 单个失败可能由多个组件共同贡献

例子：
- 完整 RAG 链对 200 条用户问题的答案准确度
- Agent 在 50 个任务上的成功率 + 步数 + 成本

### 2.3 用户级（User-level / Online）

线上真实用户的反馈、行为信号、A/B 对比。

- 唯一**真正能信**的指标
- 但不能用于开发循环（慢、稀疏、有伦理风险）
- 用来**校准**离线指标——如果离线分上升但线上反馈下降，离线评测设计有问题

### 2.4 怎么协同

```
开发期           合并前         上线后
─────           ──────         ──────
组件级 unit  →  系统级回归  →  用户级监控
（秒级）       （分钟级）       （持续）

每一层的失败都要回流到下一次的组件级测试
```

只做一层都会出问题：
- 只做组件级 → 集成到一起跑不通
- 只做系统级 → 找不到根因
- 只做用户级 → 改一个 prompt 都不知道有没有变好

## 3. Eval 的"四个角色"

任何一次评测涉及四个东西，哪个搞错都会失效：

| 角色 | 是什么 | 常见问题 |
|---|---|---|
| **Subject** | 被评测的对象（一条链 / 一个 prompt 版本 / 一个 Agent） | 多版本时不固定，结果没法比 |
| **Dataset** | 输入数据（带或不带 ground truth） | 太小 / 偏离生产 / 泄漏到训练 |
| **Metrics** | 怎么打分 | 选错指标，或指标自身不可靠 |
| **Judge** | 谁来打分（规则 / LLM / 人） | LLM 当 judge 有偏；人不一致 |

把这四个角色**显式分开**，每次评测都能讲清楚"我在测什么、用什么数据、按什么指标、谁来判"——eval 才能 reproducible。

## 4. 三类评测方法的取舍

| 方法 | 速度 | 成本 | 准确度 | 适合 |
|---|---|---|---|---|
| **确定性规则** | ⚡⚡⚡ | 0 | 高（在适用范围内） | exact match、JSON 格式、长度、关键词 |
| **启发式** | ⚡⚡ | 低 | 中 | BLEU / ROUGE / 编辑距离 / embedding 相似度 |
| **LLM-as-Judge** | ⚡ | 中 | 中-高（看模型/prompt） | 开放生成、答案质量、风格 |
| **人工** | 🐢 | 高 | 高（也有不一致） | 终极金标 / 校准前三类 |

实战推荐：
- **能用规则就用规则**：JSON 校验、URL 匹配、关键词覆盖——便宜可靠
- **能用启发式就用启发式**：检索 hit rate、引用一致性——可解释
- **必须用 LLM judge 的才用 judge**：开放问答、多步推理质量
- **关键决策点用人工**：上线前抽样、新 metric 的"地面真相"

## 5. 心智模型："离线评测预测线上效果"

整个 eval 体系的**目标**是一句话：

> **让离线指标的提升能高概率预测线上效果的提升。**

如果做不到这一点（"离线分涨了 5%、上线反而掉了"），所有进阶技巧都白搭。要做到这一点，三件事缺一不可：

1. **数据集真**：来自真实用户分布，覆盖关键场景，规模够大
2. **指标对**：度量的是真正在乎的东西，不是"好测的东西"
3. **方法稳**：同一个 subject 测两次结果一致；不同 subject 之间可比

剩下所有章节都在围绕这三件事做工。

## 6. 反模式速查

| 反模式 | 后果 | 解药 |
|---|---|---|
| 只看肉眼 / 个例 | 改一个修一片，无收敛 | 评测集 + 规模 |
| 评测集太小（< 30 条） | LLM judge 自带抖动，分数没意义 | ≥ 100，关键指标 ≥ 300 |
| 评测集泄漏到训练/prompt | 看起来准，本质作弊 | 离线集和上线集分开 |
| Cherry-pick 失败案例展示 | 局部改进、整体退化 | 每改必跑全集 |
| 用 GPT-4o 当 subject **和** judge | judge 偏向自家风格 | judge 用不同家族的模型 |
| 只看 mean 不看分布 | 一两个极端 case 拖整体 | 看 p50 / p95 / 各分组 |
| 测试目标和真实目标错位 | "翻译流畅度"高但用户根本看不懂 | 校准：定期人工抽查 |
| 改完不版本化 | 不知道哪次实验得了多少分 | 每次实验记 (commit, dataset_version, metric_version) |

## 7. 一个最小工作循环

理想的开发循环长这样：

```
        ┌──────────────────────────────┐
        │  失败 case 进 dataset         │
        └─────────────┬────────────────┘
                      │
                      ▼
              修改 subject (prompt / 模型 / 链)
                      │
                      ▼
              本地跑 mini eval（< 30s）
                      │
                      ▼
                通过？ ── 否 ──► 改
                      │ 是
                      ▼
                推 PR
                      │
                      ▼
              CI 跑全量评测（几分钟）
                      │
                      ▼
                通过？ ── 否 ──► 改 / 回退
                      │ 是
                      ▼
                合并 → 灰度上线
                      │
                      ▼
                监控 + 用户反馈
                      │
                      └──回流到失败 case → 上面循环
```

后面 9 章都是把这个循环里每一步做实。
